## 2. SQL Queries

### Slide 1 — The basic query and what the DBMS "does"

**What you need to know**
- `SELECT cols FROM tables WHERE condition`
- Meaning = **Cartesian product of FROM tables → filter with WHERE → keep the SELECT columns.** (The slides give it as π(σ(R1 × R2 × …)).)
- Several tables in `FROM` with no join condition = full Cartesian product.
- Use `R.C` when two tables have a column with the same name.

**Running example table used below**

| Student | Major | GPA |
|---|---|---|
| Alice | CS | 3.8 |
| Bob | Math | 3.5 |
| Carol | CS | 3.9 |
| Dan | Math | NULL |

```sql
SELECT Student FROM Student WHERE Major = 'CS' AND GPA > 3.85;
```
→ **Carol** only (Alice's 3.8 fails).

> **Exam Trap — `AND` vs `OR` in a join.** `WHERE a.k = b.k AND ... OR c.k = d.k` doesn't mean "also join these." `OR` lets rows through that skip the join condition (this is exactly HW 1b). Also remember `AND` binds tighter than `OR`; use parentheses (slide Q3: `Dept#=30 AND (Job='engineer' OR Job='technician')`).

---

### Slide 2 — Predicates: BETWEEN, IN, LIKE

**What you need to know**
- `C BETWEEN v1 AND v2` — **inclusive** range. `NOT BETWEEN` is the negation.
- `C IN (v1, v2, …)` or `C IN (subquery)`; `NOT IN` is the negation.
- `LIKE`: `%` = any sequence (even empty); `_` = exactly one character.

| Pattern | Matches |
|---|---|
| `'%database%'` | contains "database" |
| `'database%'` | starts with "database" |
| `'__R%'` | third character is R (slide example) |

> **Exam Trap.** `LIKE 'database'` (no wildcards) is the same as `= 'database'`. It is **not** "contains."

---

### Slide 3 — ORDER BY and DISTINCT

**What you need to know**
- `ORDER BY` default is ascending. `ORDER BY Job, Salary DESC` sorts by Job ascending, then ties by Salary descending.
- Without `ORDER BY` the result order is up to the system.
- `SELECT` does **not** remove duplicates by default; `SELECT DISTINCT` does.

```sql
SELECT DISTINCT Major FROM Student;   -- CS, Math
SELECT Major FROM Student;            -- CS, Math, CS, Math
```

---

### Slide 4 — Joins (4 ways to write one)

All of these are equivalent (slides):

```sql
SELECT DeptName FROM Employees, Departments
WHERE Name='Red' AND Employees.Dept# = Departments.Dept#;

SELECT DeptName FROM Employees JOIN Departments
  ON Employees.Dept# = Departments.Dept#  WHERE Name='Red';

SELECT DeptName FROM Employees NATURAL JOIN Departments WHERE Name='Red';

SELECT DeptName FROM Employees JOIN Departments USING (Dept#) WHERE Name='Red';
```

- `CROSS JOIN` = Cartesian product. `JOIN ... ON` = theta-join (any condition).
- `NATURAL JOIN` matches **all same-named columns**. `USING (cols)` matches only the listed ones.
- *Slide-specific note:* the slides say SQL's NATURAL JOIN does **not** drop the duplicate column the way relational-algebra natural join does.

---

### Slide 5 — Outer joins (keep the non-matching rows)

Inner join drops rows with no match. Outer join keeps them and fills with **NULL**.
- `LEFT` keeps unmatched rows of the left table; `RIGHT` the right; `FULL` both.
- `UNION JOIN` (slides): all columns and all rows of both, padded with NULLs, no matching.

Slide example: R(A,B) = {(a,1),(b,2)}, S(B,C) = {(1,x),(3,v)}

| Join | Result (A, B, C) |
|---|---|
| `R NATURAL LEFT OUTER JOIN S` | (a,1,x), (b,2,NULL) |
| `R NATURAL RIGHT OUTER JOIN S` | (a,1,x), (NULL,3,v) |
| `R NATURAL FULL OUTER JOIN S` | (a,1,x), (b,2,NULL), (NULL,3,v) |

> **Exam Trap.** LEFT/RIGHT is about *which side's unmatched rows survive*, not which side's columns appear.

---

### Slide 6 — Expressions, `AS`, virtual columns

- Expressions in `SELECT` create **virtual columns**, computed per query and not stored.
- Name them with `AS`: `SELECT Salary + Bonus AS TotalSalary`.
- Operators: `+ - * /`; functions `ABS`, `MOD`; strings use `||` for concatenation.
- *Lower priority:* `SUBSTRING`, `OVERLAY`, `TRIM`, `UPPER/LOWER`, `POSITION`, `CURRENT_DATE`, `EXTRACT`, `CAST`, `OVERLAPS`, `SIMILAR TO` appear in the slides, but nothing in HW2 uses them.

---

### Slide 7 — Aggregates and `GROUP BY`

**What you need to know**
- Aggregates: `MAX, MIN, SUM, AVG, COUNT`.
- `GROUP BY` partitions rows into groups; the aggregate runs **once per group**. With no `GROUP BY` the whole table is one group.
- **The three `COUNT`s:**

| Form | Counts |
|---|---|
| `COUNT(*)` | all rows in the group (NULLs included) |
| `COUNT(col)` | rows where `col` is **not NULL** |
| `COUNT(DISTINCT col)` | distinct non-NULL values |

- `MIN/MAX`: `DISTINCT` changes nothing. `SUM/AVG` skip NULLs.

```sql
SELECT Major, COUNT(*), COUNT(GPA), AVG(GPA)
FROM Student GROUP BY Major;
```

| Major | COUNT(*) | COUNT(GPA) | AVG(GPA) |
|---|---|---|---|
| CS | 2 | 2 | 3.85 |
| Math | 2 | 1 | 3.5 |

Math: Dan's NULL GPA is counted by `COUNT(*)` but ignored by `COUNT(GPA)` and `AVG`. (`AVG` = 3.5/1, **not** 3.5/2.)

> **Exam Trap — what can go in SELECT with GROUP BY.** The slides' rule: SELECT may contain only **GROUP BY columns** and **aggregates**. `SELECT Major, Student, MAX(GPA) ... GROUP BY Major` is invalid because `Student` is neither.

---

### Slide 8 — `HAVING` and the execution order

**Execution model (slides) — memorize the order:**
1. `WHERE` filters **individual rows**
2. `GROUP BY` forms groups
3. `HAVING` filters **groups**
4. Aggregates in `SELECT` are computed on surviving groups

```sql
SELECT Major, COUNT(*) FROM Student
WHERE GPA > 3.6            -- row filter first: Alice, Carol survive
GROUP BY Major
HAVING COUNT(*) >= 2;      -- group filter: CS has 2 -> kept
```
→ `CS, 2`

Same idea, different result:
```sql
SELECT Major, COUNT(*) FROM Student GROUP BY Major HAVING COUNT(*) >= 2;
```
→ `CS 2` and `Math 2` (Dan is counted because there's no WHERE).

> **Exam Trap — WHERE vs HAVING.** `WHERE` runs *before* grouping, so it can't use aggregates of groups. `HAVING` runs *after* grouping and (per the slides) its predicates involve aggregate functions. "Rows with GPA > 3.6" → WHERE. "Majors with ≥ 2 students" → HAVING.
>
> **Slide inconsistency:** the HAVING example is written `HAVING COUNT(*) > 2`, but the text says "at least two employees" and the shown results include groups with COUNT = 2. If the exam shows this, know the true meaning: `> 2` returns only groups of **3+**.

**Could be T/F:** *"A WHERE clause is evaluated after GROUP BY."* → **False.** (WHERE is first.)

### Slide 9 — NULL and three-valued logic

**What you need to know**
- A comparison involving NULL is **Unknown (?)**, not true or false.
- WHERE keeps a row **only if the condition is True**. False *and* Unknown rows are both dropped.
- `AND`/`OR`/`NOT` truth tables (slides):

| AND | T | F | ? |  | OR | T | F | ? |  | NOT |  |
|---|---|---|---|---|---|---|---|---|---|---|---|
| **T** | T | F | ? |  | **T** | T | T | T |  | T → F |  |
| **F** | F | F | F |  | **F** | T | F | ? |  | F → T |  |
| **?** | ? | F | ? |  | **?** | T | ? | ? |  | ? → ? |  |

Shortcuts: `F AND ?` = **F**; `T OR ?` = **T**; `T AND ?` = **?**; `F OR ?` = **?**; `NOT ?` = **?**.

- Test with `IS NULL` / `IS NOT NULL`. **`= NULL` never works.**
- Arithmetic with a NULL → NULL (`Salary + Bonus` is NULL if Bonus is NULL).
- Aggregates **ignore NULLs**, so `SUM(c1 + c2)` can differ from `SUM(c1) + SUM(c2)`.
- Two NULLs are **not equal** (`NULL = NULL` is Unknown) but are **not distinct**: `DISTINCT` and `GROUP BY` collapse them into one.
- `IS DISTINCT FROM`: like `<>` but NULL-safe (two NULLs → FALSE).

**Slide example:** R(A,B,C): t1 = (a, NULL, c1), t2 = (a1, b, c2), t3 = (a2, NULL, NULL)

| Query | Result | Why |
|---|---|---|
| `WHERE A='a' OR B='b'` | t1, t2 | t1: T OR ? = T; t2: F OR T = T; t3: F OR ? = ? |
| `WHERE A='a' AND B='b'` | none | t1: T AND ? = ?; t2: F; t3: F |
| `WHERE NOT C='c1'` | t2 | t1: NOT T = F; t2: NOT F = T; t3: NOT ? = ? |
| `WHERE B IS NULL` | t1, t3 | |

On the Student table: `GPA > 3.6` → Alice, Carol. `NOT (GPA > 3.6)` → **Bob only**, and **Dan appears in neither**.

> **Exam Trap.** `B = B`, `B='b' OR B<>'b'`, and `B IS NOT NULL` are **all equivalent** (slide). Rows with NULL vanish from all three. Also: constraints are *not violated* when their predicate evaluates to Unknown.

**Multiple-answer style:** With the Student table, which are true?
A. `SELECT COUNT(*)` returns 4 · B. `SELECT COUNT(GPA)` returns 4 · C. `SELECT AVG(GPA)` divides by 3 · D. `WHERE GPA = NULL` returns Dan
→ **A and C true.** B false (3). D false (Unknown, returns nothing).

### Slide 10 — Subqueries: scalar vs table

**What you need to know**
- A subquery in WHERE supplies comparison value(s) to the outer query. It's run once (uncorrelated).
- **Scalar subquery** = returns one value → can use `=, >, <`. If it returns several rows → **runtime error**.
- **Table subquery** (multiple values) → needs `IN`, `ANY`/`SOME`, or `ALL`.
- Shorthands: **`IN` ≡ `= ANY`**, **`NOT IN` ≡ `<> ALL`**.

Table `Emp`:

| Name | Dept | Salary |
|---|---|---|
| Ann | 10 | 1000 |
| Bo | 10 | 3000 |
| Cy | 20 | 1500 |
| Di | 20 | 1700 |

```sql
SELECT Name FROM Emp WHERE Salary > ANY (SELECT Salary FROM Emp WHERE Dept=20);
```
Subquery set = {1500, 1700}. `> ANY` means "bigger than at least one" (i.e., > 1500) → **Bo, Di**.

```sql
SELECT Name FROM Emp WHERE Salary > ALL (SELECT Salary FROM Emp WHERE Dept=20);
```
`> ALL` means "bigger than every one" (> 1700) → **Bo**.

**The "maximum" pattern (HW 1e):** `HAVING COUNT(*) >= ALL (SELECT COUNT(*) ... GROUP BY ...)` — a group whose count is ≥ every group's count = the biggest.

> **Exam Trap.** `= (subquery returning many rows)` is an error, so use `IN`. `<ANY` and `>ALL` are not interchangeable: `ANY` is "at least one," `ALL` is "every one." Applying the NULL rules *(extra clarification)*: `x NOT IN (list containing NULL)` can never be True, so it returns no rows.

---

### Slide 11 — Correlated subqueries

**What you need to know**
- **Uncorrelated:** subquery runs once. **Correlated:** subquery references a column of the *outer* row, so it is re-evaluated **for each candidate outer row**.
- If the subquery uses the **same table** as the outer query, the outer table needs an **alias**, and the subquery uses that alias to refer to the outer row. (Alias is optional but good practice for different tables.)

```sql
-- Correlated: above the average of MY OWN department
SELECT Name FROM Emp X
WHERE Salary > (SELECT AVG(Salary) FROM Emp WHERE Dept = X.Dept);
```
Dept 10 avg = 2000 → Bo (3000) passes. Dept 20 avg = 1600 → Di (1700) passes. **Result: Bo, Di.**

```sql
-- Similar looking, NOT correlated: above the OVERALL average
SELECT Name FROM Emp WHERE Salary > (SELECT AVG(Salary) FROM Emp);
```
Overall avg = 1800 → only Bo. **Result: Bo.**

> **Exam Trap.** Two queries that differ only by a correlation (`X.Dept`) can return different rows, as above.

Aliases are also needed when you compare **two rows of the same table** in a join: `FROM Employees X, Employees Y ... X.Salary > Y.Salary`.

### Slide 12 — EXISTS / NOT EXISTS / UNIQUE / Division

- `EXISTS(sq)` = True if the subquery returns **at least one row**; `NOT EXISTS` = True if it returns none. **They never return Unknown** (slide).
- `UNIQUE(sq)` = True if the subquery has **no duplicate** rows; also never Unknown.
- `NOT EXISTS` is the way to say "has no …" or to simulate `EXCEPT`/`INTERSECT` if unsupported.
- **Division ("for ALL …")** = **double `NOT EXISTS`** ("there is no project for which this department doesn't participate"). Slides: "based on the notion of counterexample."

```sql
-- employees who manage someone (at least one report)
SELECT Name FROM Employees X
WHERE EXISTS (SELECT * FROM Employees WHERE X.Emp# = Reports_to);
```

---

### Slide 13 — Set operations

**What you need to know**
- `UNION`, `INTERSECT`, `EXCEPT` (also called `MINUS`).
- Both queries must have the **same number of columns with compatible domains**. Columns are matched by **position**, not name (unless `CORRESPONDING` is used).
- `UNION` **removes duplicates**; `UNION ALL` **keeps** them (faster; use when you know there are none).
- `ORDER BY` goes **once, at the very end**, and refers to column **positions** (`ORDER BY 2`).

```sql
SELECT Name FROM Part_Time_Employees
EXCEPT
SELECT Name FROM In_Sabbatical_Employees;     -- part-time but NOT in sabbatical
```

> **Exam Trap.** `UNION` of {1,2,2} and {2,3} → {1,2,3}; `UNION ALL` → {1,2,2,2,3}. Another: `ORDER BY` after *each* SELECT of a UNION is not allowed.

### Slide 14 — DML: INSERT, DELETE, UPDATE

**INSERT**
```sql
INSERT INTO R [(C1,...,Cn)] { VALUES (e1,...,en) | subquery };
```
- Values are matched to columns by **position**.
- Columns you don't list get **NULL or their DEFAULT**.
- `INSERT ... SELECT` inserts every row returned by the subquery (and `VALUES` and a subquery are mutually exclusive).

**DELETE**
`DELETE FROM R [alias] [WHERE F];` → **no WHERE = deletes all rows.**

**UPDATE**
```sql
UPDATE R [alias] SET C1 = {expr | NULL}, ... [WHERE F];
```
- **No WHERE = updates all rows.**
- Subqueries may pick the rows (`WHERE Emp# IN (SELECT ...)`) or compute the new value (`SET Salary = (SELECT 1.1*AVG(Salary) ...)`).
- **Set-oriented semantics:** the WHERE and the SET expressions are evaluated **once**, then all rows change "simultaneously."
- `SET B = NULL` (keyword) is not the same as `'NULL'` (string).

```sql
-- HW 1g pattern: give Bob's thesis Mary's supervisor
UPDATE Theses
SET Prof# = (SELECT Prof# FROM Students, Theses WHERE Students.S#=Theses.S#
             AND FName='Mary' AND LName='Rossi')     -- NEW value comes from Mary
WHERE S# = (SELECT S# FROM Students WHERE FName='Bob' AND LName='Smith');  -- row to change = Bob's
```

> **Exam Trap.** `SET` side = who receives the value; `WHERE` side = which row is modified. Swapping Bob and Mary reverses the update.

## 3. SQL Views (slides 74–100)

### Slide 15 — What a view is and why it exists

**What you need to know**
- A view is basically a **saved query you can treat like a table**. It is a virtual table; its data is **recomputed from the base tables whenever you use it** (slides: "computed from the base table each time the view is materialized").
- Uses (slide): **simplify data access**, provide **logical independence**, assure **data confidentiality** (show only some columns/rows).
- Syntax:
```sql
CREATE VIEW V [(ColumnNameList)] AS Q [WITH [LOCAL|CASCADED] CHECK OPTION];
```
- The view name must be **unique** among the user's relations and views.
- The view has **as many columns as Q's SELECT list**.
- **`ColumnNameList` is mandatory** when the query has **aggregates or expressions** (virtual columns need a name).
- Once created, a view is "(almost) a base table" for queries.

```sql
CREATE VIEW Emp10 AS
SELECT Emp#, Name, Job FROM Employees WHERE Dept# = 10;

SELECT * FROM Emp10;     -- query it like a table
```

> **Exam Trap.** A view does not keep its own copy of the data. If base rows change, the view's output changes too. *(Extra clarification: "materialized views" that DO store data exist in real systems, but the slides don't cover them. Don't confuse the slide's phrase "materialized" with that.)*

**Could be T/F:** *"A view always stores a separate copy of the underlying data."* → **False.**

---

### Slide 16 — Views with joins, expressions, aggregates

```sql
CREATE VIEW Personnel AS                       -- join
SELECT Name, Job, ProjName FROM Employees, Projects
WHERE Employees.Proj# = Projects.Proj#;

CREATE VIEW V1 (Name, Monthly_Salary, Yearly_Salary, Dept#) AS   -- expression -> needs names
SELECT Name, Salary, Salary*12, Dept# FROM Employees;

CREATE VIEW Dept_S (Dept#, Min_S, Avg_S, Max_S, Total) AS         -- aggregate -> needs names
SELECT Dept#, MIN(Salary), AVG(Salary), MAX(Salary), SUM(Salary)
FROM Employees GROUP BY Dept#;
```

---

### Slide 17 — How a query on a view runs

- The system **replaces the view name with its definition** and runs the combined query.

```sql
SELECT Name, ProjName FROM Personnel WHERE Job='manager';
-- becomes:
SELECT Name, ProjName FROM Employees, Projects
WHERE Employees.Proj# = Projects.Proj# AND Job='manager';
```
- **Restriction (slides):** you can't apply an aggregate function to a view column that is itself defined by an aggregate. This composition is impossible (some DBMS allow it anyway).

---

### Slide 18 — Updating through a view (the 3 problems)

Changes on a view propagate to the base table(s). It's ambiguous when the view isn't a simple slice of one table:

| Problem | Example | Why it's a problem |
|---|---|---|
| **1. Insert** | View `V3` omits `Salary`, `Bonus` | What values go in the hidden columns? Use **default**, or **NULL** (bad if they're NOT NULL). |
| **2. Delete** | View `V4` joins Employees and Departments | Delete the employee? the department? both? The slide shows deleting Red also removed everyone sharing his office from the view. Different translations are possible, so many DBMS refuse updates on **join views**. |
| **3. Update** | `V5 (Emp#, TotalSalary) = Salary + Bonus` | Raise Salary? Bonus? Both? You'd need the inverse of the expression. |

---

### Slide 19 — The updatability rules (HIGH YIELD, used in HW 2 and 3)

| Operation | Allowed when the view definition query… |
|---|---|
| **DELETE** | is on **one table** and has **no `GROUP BY`, no `DISTINCT`, no aggregates** |
| **UPDATE** | meets the DELETE conditions **and** the column being modified is **not defined by an expression** |
| **INSERT** | meets the conditions above **and** every column that is **NOT NULL with no default** is **included in the view** |

(The slides label these "Examples of restrictions," so they aren't claimed to be a complete list.)

**Apply to HW 2 (`V1` = `SELECT Title, Evaluation FROM Theses WHERE Topic='DB'`):**
- SELECT ✔ · DELETE ✔ (one table, plain) · UPDATE Title ✔ · UPDATE Evaluation ✔
- INSERT ✘ because the NOT NULL primary key `T#` is missing from the view.

> **Exam Trap.** A view can be updatable for some columns and not others (`UPDATE` of an expression column ✘, of a plain column ✔). Check *column by column*.

---

### Slide 20 — `WITH CHECK OPTION`

**The problem:**
```sql
CREATE VIEW EmpHS AS
SELECT Emp#, Name, Salary FROM Employees WHERE Salary > 3000;
INSERT INTO EmpHS VALUES (200, 'Haas', 2000);
```
Without CHECK OPTION: the row is **inserted into the base table**, but it **doesn't satisfy the view's WHERE**, so it **never appears in the view** ("disappearing row").

**With `WITH CHECK OPTION`:** inserts/updates through the view are **rejected** if the new row wouldn't satisfy the view's condition. The `Haas, 2000` insert fails.

**`LOCAL` vs `CASCADED`** only matter when a view is built **on another view**. If V1 is defined on V2:
- **LOCAL:** new rows must satisfy V1's condition, and V2's condition **only if V2 also has a check option**.
- **CASCADED:** new rows must satisfy V1's condition **and** V2's (regardless of whether V2 has a check option).

**HW 2, Q4:** `V3 ... WHERE Topic='DB' WITH CHECK OPTION` → insert with `'Security'` → **NO**; insert with `'DB'` → **YES**.

> **Exam Trap.** CHECK OPTION checks the **inserted/updated row against the view's WHERE**. It isn't about primary keys or types.

---

### Slide 21 — Dropping, renaming, redefining views

- `DROP VIEW V;`  `RENAME V1 TO V2` (slide's notation).
- **You cannot modify a view's definition. The only way is to redefine it.**
- `DROP TABLE` / `DROP VIEW` accept:
  - `RESTRICT` → drop only if **no other view** (or schema element) depends on it
  - `CASCADE` → also drops the **dependent views**

---

### Slide 22 — Catalogs (lower priority)

- Catalogs = a **system database of metadata** about tables, views, constraints, indexes, permissions, **stored as ordinary relations**.
- Examples: `SYSTABLES` (name, creator, **type T/V/A**, column count), `SYSCOLUMNS` (column name, table, position, type). Names differ per DBMS.
- You can **query** them like tables (`SELECT TABNAME FROM SYSTEM.SYSCOLUMNS WHERE COLNAME LIKE 'S%'`).
- In general you **can't modify** them directly. The DBMS updates them when you run DDL. (Exception: DBAs can modify catalog **statistics** used by the optimizer.) Entries for the catalog tables themselves are "hard-wired" at install.
- Views are often defined *on top of* catalog tables.

## 4. Triggers (Active Databases)

### Slide 23 — Passive vs active DBMS; why triggers exist

- **Passive DBMS:** runs operations only when asked. **Active DBMS:** reacts **by itself** to events by running **active rules = triggers**.
- Without triggers, you'd either **poll** (too often = wasteful; too seldom = miss things) or put monitoring code in every application (hurts modularity; changes require app changes).
- Uses: integrity constraints, alerting, auditing, security, statistics, views/derived data.

### Slide 24 — The ECA model: Event → Condition → Action

```
ON event  IF condition  THEN action
```
1. The **event** happens → the trigger is **activated**.
2. The **condition** is checked.
3. If true → the **action** runs. **No condition = always true** (slides).

- *Why have an event at all?* Detecting an event is cheap; evaluating a condition continuously is expensive. Also, the same condition can have different actions for different events.
- (AI "production rules" are just IF–THEN with no event.)

**Event types (slides):** data modifications (INSERT/DELETE/UPDATE), data accesses (queries), DBMS operations (login, transactions), temporal events, application-defined events. Events can be combined (and/or, sequence, temporal composition).
**Condition:** SQL predicates, queries, or procedure calls; can refer to **old and new** values.
**Action:** data modifications, queries, other commands (DDL, commit/rollback, grant/revoke), or procedure calls.

**Example (slides):** Inventory, if quantity drops below 4 → order 100 items.

| | |
|---|---|
| **Event** | A sale updates `Inventory.Quantity` |
| **Condition** | the new quantity < 4 |
| **Action** | insert an order for 100 items |

### Slide 25 — Execution model

- **Two activities:** (1) detect events and activate rules; (2) the **reactive process**: select a rule → evaluate its condition → if true, execute the action.
- Rule selection among several activated rules: **non-deterministic choice among the highest-priority** ones (priority can be relative or absolute).
- **Instance-oriented** (row-level): runs **once per affected tuple.** **Set-oriented** (statement-level): runs **once for the whole set.** They can leave the database in **different states** (slide example: add $5K + average salary; set-oriented gives all inserted rows the **same** salary, instance-oriented gives them **different** salaries).
- **Termination problem:** rules can trigger each other forever. Remedies: designer care, a cap on activations, syntactic restrictions (no cycles, etc.). **Oracle's default: 32 recursive calls.**
- **Transition tables:** hold the tuples **actually** inserted/deleted/modified (for updates: before and after versions); they make condition checks more efficient.

### Slide 26 — Oracle trigger syntax

```sql
CREATE [OR REPLACE] TRIGGER Name
{BEFORE | AFTER | INSTEAD OF}
{DELETE | INSERT | UPDATE [OF col, ...]} [OR ...]
ON Relation
[REFERENCING OLD AS o NEW AS n]
[FOR EACH ROW]
[WHEN (Condition)]
{PL/SQL block | CALL procedure}
```
- Manage with `ALTER TRIGGER ... ENABLE/DISABLE` and `DROP TRIGGER`.
- Multiple events joined by **OR**. Inside the body, tell them apart with `IF INSERTING`, `IF DELETING`, `IF UPDATING`, `IF UPDATING('col')`.
- Events can also be DDL (CREATE/ALTER/DROP), startup/shutdown, errors, logon/logoff; the course focuses on database commands.

**Worked example (adapted from slide example 3):**
```sql
CREATE TRIGGER Reorder
AFTER UPDATE OF Availability ON Inventory      -- EVENT
FOR EACH ROW
WHEN (new.Availability < new.MinQty)           -- CONDITION
BEGIN
  INSERT INTO PendingOrders VALUES (:new.ProdCode, :new.OrderQty, SYSDATE);   -- ACTION
END;
```

### Slide 27 — Types of trigger: BEFORE/AFTER × ROW/STATEMENT, and INSTEAD OF

| | **STATEMENT** | **ROW** |
|---|---|---|
| **BEFORE** | once, before the triggering command | before **each** affected tuple |
| **AFTER** | once, after the command | after **each** affected tuple |

- **On tables:** these 4 types. **On views:** `INSTEAD OF` triggers (always ROW-level).
- `INSTEAD OF` runs **in place of** the command. It lets you do updates on views that can't be updated directly (e.g., `DELETE` on an aggregate view: the trigger modifies the base table).

**Which to choose (slides):**
- **Row-level** if the action depends on each modified row's values.
- **Statement-level** if the action is global (one audit record, an authorization check, an aggregate).
- **BEFORE** if the trigger decides whether the command should run at all (avoids execute-then-rollback) or **derives column values** for the insert/update.

**Order of execution (Oracle slide):** BEFORE STATEMENT → for each row: BEFORE ROW → *command + integrity-constraint check* → AFTER ROW → AFTER STATEMENT. Several triggers of the same type run in **non-deterministic order**.

### Slide 28 — Oracle rules & restrictions (very testable)

| Rule | Detail |
|---|---|
| **Condition (`WHEN`)** | Only for **ROW** triggers; only SQL predicates on the modified tuple; **no subqueries, no user-defined functions**. Statement triggers do checks in the PL/SQL block. |
| **Old/new values** | In the **action**: `:old` and `:new`. In the **WHEN condition**: `old` and `new` (no colon). |
| **Action restrictions** | PL/SQL block or procedure call. **No DDL and no transaction commands (e.g., `ROLLBACK`)**. |
| **Raising errors** | Use `raise_application_error(code, msg)` to return an error to the calling transaction (which can then roll back). |
| **Mutating table** | The table on which the triggering statement is running. **Row triggers can't read or modify (INSERT/DELETE/UPDATE) it.** Reason: data may be inconsistent / order-dependent. Workaround: auxiliary tables. |
| **Error in action** | Aborts the trigger's execution unless handled by an exception in the action. |
| **Termination** | Timeout, default **32 recursive calls** (changeable). |
| **INSTEAD OF** | Views only, always row-level. |

> **Exam Trap — a pile of classic wrongs:** (1) `WHEN` on a statement-level trigger ✘; (2) `ROLLBACK` inside a trigger body ✘; (3) `INSTEAD OF` on a table ✘; (4) `:new` in the WHEN clause (it's `new`) ✘; (5) a row trigger reading the table it fires on ✘ (mutating).

### Slide 29 — Slide examples to be able to read

- **Verify_Salary** (`BEFORE INSERT OR UPDATE OF Salary, Job ... FOR EACH ROW WHEN (new.Job <> 'president')`): looks up the allowed range for the job and calls `raise_application_error` if the salary is outside it. *BEFORE is used because the trigger decides whether the change is allowed.* (Example 2's `WHEN (new.Salary <> 'president')` in the slides looks like a typo for `new.Job`.)
- **OrderProducts** (AFTER UPDATE OF Availability, row-level, WHEN below the minimum): inserts a pending order if none exists.
- **Total_Salary:** keeps a derived `TotalSalary` per department in sync with `AFTER DELETE OR INSERT OR UPDATE`, using `IF DELETING / INSERTING / UPDATING` and `:old/:new`.
- **Example 5 (reservations):** BEFORE INSERT trigger that creates/updates the agency row and raises an exception when a limit of three is reached.

## 6. Final High-Yield Review

**1. Syntax patterns**
```sql
SELECT [DISTINCT] cols FROM t1, t2 WHERE join_cond AND filter
GROUP BY cols HAVING agg_condition ORDER BY col [DESC];
... WHERE col IN (SELECT ...)         ... WHERE col > ALL (SELECT ...)
... WHERE EXISTS (SELECT * FROM t WHERE t.k = outer.k)
q1 UNION [ALL] q2 ;   q1 EXCEPT q2 ;   q1 INTERSECT q2
INSERT INTO t (cols) VALUES (...) | SELECT ... ;
UPDATE t SET c = expr [WHERE ...] ;   DELETE FROM t [WHERE ...] ;
CREATE VIEW v [(cols)] AS select [WITH [LOCAL|CASCADED] CHECK OPTION];
CREATE TRIGGER n {BEFORE|AFTER|INSTEAD OF} event ON t [FOR EACH ROW] [WHEN (cond)] body
```

**2. Conceptual distinctions**
- WHERE (rows, before grouping) ↔ HAVING (groups, after grouping)
- `COUNT(*)` ↔ `COUNT(col)` ↔ `COUNT(DISTINCT col)`
- `IN`/`= ANY` ↔ `ALL`; scalar ↔ table subquery
- Correlated (re-run per outer row) ↔ uncorrelated (run once)
- `UNION` ↔ `UNION ALL`; inner ↔ outer join
- `= NULL` ✘ ↔ `IS NULL` ✔
- `DISTINCT`/`GROUP BY` treat NULLs as the same; `=` treats them as Unknown

**3. Views**
Virtual, recomputed from base tables · syntax · column names mandatory for expressions/aggregates · query = substitute the definition · DELETE needs single table, no GROUP BY/DISTINCT/aggregates · UPDATE also needs a non-expression column · INSERT also needs all NOT NULL no-default columns present · CHECK OPTION rejects rows that fail the view's WHERE · LOCAL/CASCADED only matter with nested views · can't alter a definition (redefine) · RESTRICT/CASCADE on drops.

**4. Triggers**
ECA · no condition = always true · BEFORE (decide/derive) vs AFTER · ROW (per tuple) vs STATEMENT (once) · `WHEN` only on row triggers, no subqueries · `:old/:new` in body, `old/new` in `WHEN` · `INSTEAD OF` = views only, always row · mutating table restriction · no ROLLBACK/DDL in action; use `raise_application_error` · 32-call recursion default.

**5. Most common traps**
`LIKE` without `%` · `OR` inside join conditions · aggregates in `WHERE` · non-grouped column in `SELECT` with `GROUP BY` · NULL comparisons · `AVG` dividing by non-null count · `= (multi-row subquery)` · UNION column order/`ORDER BY` placement · UPDATE/DELETE without WHERE · "views store data" · insert into a view missing a NOT NULL column · CHECK OPTION checking the wrong thing · triggers: `WHEN` on statement-level, `ROLLBACK` in the body, `INSTEAD OF` on a table.

**6. Things to answer without notes**

- Say in which order WHERE, GROUP BY, HAVING, and SELECT-aggregates execute.
- Evaluate `T AND ?`, `F AND ?`, `T OR ?`, `F OR ?`, `NOT ?`.
- Translate "the max" or "at least two" into a subquery / HAVING.
- List the conditions for DELETE / UPDATE / INSERT on a view.
- Decide if an insert passes a CHECK OPTION view.
- Name the 4 table trigger types and what `INSTEAD OF` is for.
- Say what a "mutating table" is and what a row trigger can't do to it.

### Answers and Explanations

**Q1 — False.** A view is a virtual table; its rows are computed from the base tables when used.

**Q2 — False.** `GPA = NULL` is Unknown for every row, so nothing is returned. Use `GPA IS NULL`.

**Q3 — A, B, C true.** `COUNT(*)` counts all 4 rows. `COUNT(GPA)` ignores Dan's NULL, so 3. `AVG` also ignores NULLs, so it's (3.8+3.5+3.9)/3. D is false: there are only 2 distinct majors.

**Q4 — A and B true.** CS = 2, Math = 2 (Dan is counted by `COUNT(*)`), so both groups pass → 2 rows. C false (HAVING comes after GROUP BY). D false (WHERE can't filter on a group aggregate).

**Q5 — False.** Dan's GPA is NULL: both comparisons are Unknown, and Unknown OR Unknown = Unknown, so Dan is dropped. 3 rows.

**Q6 — A, C, D true.** Dept 20 salaries are {1500, 1700}. `> ALL` means above 1700, so only Bo (B is false). That equals `Salary > 1700` (C). With `ANY` it would mean above 1500, so Di (1700) joins Bo (D).

**Q7 — False.** Correlated version: dept avgs are 2000 and 1600 → Bo (3000>2000) and Di (1700>1600). Uncorrelated: overall avg 1800 → only Bo.

**Q8 — False.** `Name` isn't in the `GROUP BY` and isn't an aggregate. The slides allow only GROUP BY columns and aggregates in SELECT.

**Q9 — True.** Slide: `IN` ≡ `= ANY`, `NOT IN` ≡ `<> ALL`.

**Q10 — False.** `UNION` eliminates duplicates; only `UNION ALL` keeps them.

**Q11 — A, B, D true.** C is false: a single `ORDER BY` goes at the end of the whole UNION, using column positions.

**Q12 — False.** `EXISTS` and `NOT EXISTS` always return True or False (never Unknown) per the slides.

**Q13 — True.** No `WHERE` means all rows are affected (the same is true for `UPDATE` without `WHERE`). The table definition stays; only the rows go.

**Q14 — False.** The column list is **mandatory** when the query has expressions (or aggregates) so the virtual column gets a name.

**Q15 — A, B, C true; D false.** One table, no GROUP BY/DISTINCT/aggregates → SELECT and DELETE are fine. `Salary` is a plain column → UPDATE is fine. INSERT fails because `Name` (NOT NULL, no default) isn't in the view. This is the same reasoning as HW 2, Q2.

**Q16 — A, C true.** B false (has GROUP BY and aggregate). D false. The list is required because of the aggregate.

**Q17 — False.** CHECK OPTION **rejects** the insert because Salary 1500 doesn't satisfy `Salary > 2000`. The "inserted but invisible" outcome happens only *without* CHECK OPTION.

**Q18 — True.** (Slide: the difference is relevant only when a view is defined on another view.)

**Q19 — B, C true.** A false: the slides say definitions can't be modified. D false: RESTRICT refuses to drop if dependents exist.

**Q20 — B, D true.** A false (`WHEN` is for row triggers only). C false (no transaction commands like ROLLBACK; use `raise_application_error`).

**Q21 — False.** No condition = the condition is assumed always true, so the action runs whenever the event occurs.

**Q22 — True.** Statement-level = once; row-level = per affected tuple.

**Q23 — False.** That's the **mutating table** restriction: row triggers can't read or modify the table the triggering statement is changing.

**Q24 — A, B true.** C and D describe AFTER triggers (and D is also a statement-level use).
